# 失败记录与洁净复跑：哪些地方真的坏过，最后怎样证明通过

## 什么叫本次的“洁净复跑”

并不是简单地再次执行验证脚本，而是尽量删除或隔离上一轮运行状态：

- 公共 DuckDB 从源 CSV 重建。
- MetricFlow 执行 `dbt clean`，重新 seed、build、compile、query。
- Cube 执行 `docker compose down -v`，重新启动并等待 API ready。
- Wren 删除生成的 `target/`，重新 validate/build/query。
- DataHub 执行 `datahub docker nuke`，新建 MySQL/OpenSearch/Kafka volumes，重新采集。
- OpenMetadata 执行 compose `down -v`，将旧 bind volume 精确移动到 ignored runtime，创建全新 volume 后重跑。
- LinkedIn 重建路线将旧 `results/` 移入 ignored runtime，重新建图并重新调用大模型。

每一个命令都通过 [`tools/run_logged.py`](../../tools/run_logged.py) 执行。每步目录固定包含：

```text
request.json   # cwd、argv、主机信息；不记录 secret value
stdout.txt
stderr.txt
result.json    # exit code、耗时、stdout/stderr hash、声明产物 hash
```

机器可读总索引在 [`evidence_manifest.json`](evidence_manifest.json)。最终 7 个终态检查全部通过，未留下未解释失败。

## 洁净复跑中保留的 8 次诊断性失败

这些记录没有被删除，因为它们比“全部绿色”更能说明真实部署条件。

### 1. 公共数据重建：相对路径依赖

失败：`00-common-rebuild`。

```text
No files found that match the pattern "data/device_orders.csv"
```

原因：脚本内 SQL 的 CSV 路径相对于当前工作目录，而第一次从仓库根目录启动。

修复：以 `demos/common` 为 cwd 重跑。结果 16 条设备订单、3 条产品、3 条销售订单；golden SQL 校验通过。

启发：数据 recipe 中的相对路径必须明确相对谁；生产编排器应固定工作目录或传绝对 URI。

### 2. MetricFlow：必需环境变量未显式传入

失败：`11-metricflow-build`。

```text
Env var required but not provided: 'MF_DUCKDB_PATH'
```

修复：在运行环境中显式传入 DuckDB 绝对路径。后续最终 rebuild 显示 `INSERT 16`、3 metrics、1 semantic model，验证通过。

启发：连接参数是运行合同的一部分，不能依赖上一 shell 的隐式状态。

### 3. Cube：端口已开不代表 API ready

失败：`22-cube-query`。

```text
RemoteDisconnected: Remote end closed connection without response
```

原因：Cube 容器已接受 TCP 连接，但服务仍在初始化。

修复：readiness loop 同时捕获 HTTP/URL/OSError/connection close，再重试 `/meta`。后续 `/sql`、`/load` 和 golden 校验通过。

启发：生产健康检查要验证目标 API，不要只检查容器 `running` 或端口监听。

### 4. DataHub：子工作目录下的可执行文件路径

失败：`43-datahub-schema-ingest`。

```text
FileNotFoundError: lab/.venv/bin/datahub
```

原因：logger 切换 cwd 到 demo 目录后，相对 executable 不再存在。

修复：命令改为绝对路径。连接器随后产出 35 个事件，无 sink failure。

### 5. DataHub：写入后立即查询的最终一致性

失败：`47-datahub-verify`。

当时实体、中文说明、字段已经可读，但 `get_dataset_queries.total=0`。OpenSearch 刷新后变成 2。

启发：catalog entity store、search index、lineage index 和 query index 可能有不同可见时刻。agent tool 层需要有针对性的 retry/backoff，并在返回中区分“未找到”和“索引尚未刷新”。

### 6. DataHub：把搜索排名和血缘数量写死

失败：`47b-datahub-verify-after-index-refresh`。

索引刷新后：

- `device_orders_by_product` view 排在搜索第一；权威基础表排第二。
- `get_lineage` 返回 1 个 dashboard，而不是预期的 chart+dashboard 两个节点。

原始断言错误地要求“权威表必须第一”和“下游必须等于 2”。修复后的业务断言是：

- 权威表存在于候选集；
- 它的 description/term/required_filter 都正确；
- 下游集合包含指定 PowerBI dashboard；
- query count 为 2。

启发：验证 API 的语义事实，不要把搜索排序和图的展示投影当作固定合同。

### 7. LinkedIn 路线：SQL 结果正确但行顺序不同

失败：`72-linkedin-agent-real-llm`。

模型生成的 SQL 没有 `ORDER BY`，因此 DuckDB 返回 Network、IoT、Compute。每行数值都正确，但原 verifier 用列表顺序直接比较 golden CSV，得到 `matches_golden=false`。

修复：按业务键 `product_l1` 排序后比较。随后从空结果目录重新建图，再执行 5 次真实 LLM 调用，结果为 5/5 success、0 fallback、golden match。

启发：除非问题显式要求顺序，SQL 答案的等价性应按集合/多重集合和数值容差验证，而不是文本或行序完全相等。

### 8. 证据 manifest：扫描到自己的半成品目录

失败：`90-build-evidence-manifest`。

logger 先创建 step 目录、再启动 manifest builder；builder 扫描到自己的目录时 `result.json` 尚未生成。

修复：manifest 跳过缺少 `result.json` 的在途 step。最终索引报告 `unexpected_failure_count=0`。

## 补充：自然语言 → DSL 实验没有隐藏的失败

在原洁净复跑完成后，又增加了路线一的真实 LLM 规划实验。完整记录在 [`runs/20260804-nl-to-dsl`](../../runs/20260804-nl-to-dsl/README.md)：

- 一次相对 executable 路径失败，改用绝对路径后 Wren validate 成功。
- 第一轮 10 次调用通过 9 次；Cube 缺少歧义 AI context，错误地把“金额”映射成单一指标。
- 增加 Measure `meta.ai_context` 后，歧义判断修复。
- 第二轮暴露验证器过度要求排序，以及 Wren 把过滤字段误放进分组的真实规划错误。
- 最终第三轮 10/10，4 个可执行查询全部与 golden result 一致；三轮总计 30 次真实调用、0 份预写 fallback。

这些补充失败不计入早期 `evidence_manifest.json` 的 7 套终态检查；它们由新的运行目录和 `nl_to_dsl/results` 独立保存，避免事后改写旧 manifest 的含义。
