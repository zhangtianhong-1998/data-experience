# 路线 2：DataHub、OpenMetadata 的资产怎样采集，SDK/MCP 实际返回什么

## 先回答“资产是怎么来的”

DataHub 和 OpenMetadata 都不是把整张业务数据复制进知识图谱。本次关闭 profiling/sample data，仅采集与补充元数据。典型链路是：

```text
数据库系统表 / information_schema / 视图定义
    → 连接器标准化为平台实体
    → 表、字段、类型、约束、view SQL、服务/schema 层级

BI / ETL / dbt 元数据 API 或导出文件
    → dashboard、chart、job、model 等实体
    → 输入输出关系变成 lineage edge

查询日志
    → SQL parser 提取表、字段、join、filter、aggregation
    → Query 实体、usage 统计、常用查询和潜在列级血缘

人工或自动治理
    → SDK/API 写入中文说明、术语、owner、tag、认证/废弃、权限规则
```

因此，“采集”至少有两类动作：

- **自动观察到的事实**：物理字段、数据类型、主键、视图 SQL、查询日志、技术血缘。
- **后续附加的业务声明**：指标解释、必须过滤的组织、单位、负责人、认证状态。

两者必须保留来源。前者不等于业务真理，后者也不能假装是自动发现的事实。

## 一、DataHub：从连接器事件到 MCP 上下文

### 1. 洁净环境

执行 `datahub docker nuke` 后重新启动官方 quickstart：

- DataHub GMS：`v1.5.0.6`
- DataHub CLI：`1.6.0`
- 官方 MCP server：`0.6.0`
- 后端：MySQL、OpenSearch、Kafka

随后从 CSV 重建 SQLite，实际行数为：

```json
{
  "device_orders": 16,
  "product_master": 3,
  "sales_orders": 3,
  "view_count": 1
}
```

这一步的证据是 [`source_build.json`](../demos/route2/datahub/results/source_build.json)。

### 2. 数据库连接器输入是什么

recipe 在 [`ingest_sqlite.yml`](../demos/route2/datahub/ingest_sqlite.yml)，核心逻辑是用 DataHub 的 SQLAlchemy source 连接本地 SQLite、采集 schema/view/lineage，并把 metadata change proposals 发给 GMS。

真实运行报告：

```text
tables_scanned: 3
views_scanned: 1
events_produced: 33
dataset/Table: 3
dataset/View: 1
schemaMetadata: 4
viewProperties: 1
upstreamLineage: 1
fineGrainedLineages: 1
failures: []
```

连接器在内部完成这些标准化：

| SQLite 信息 | DataHub 对象/Aspect |
|---|---|
| 数据库与 `main` schema | Container + container hierarchy |
| `device_orders` | Dataset URN：`urn:li:dataset:(urn:li:dataPlatform:sqlite,main.device_orders,PROD)` |
| 10 个字段 | `schemaMetadata.fields` |
| `order_id` 主键 | 字段 `isPartOfKey=true` |
| `device_orders_by_product` view | Dataset subtype=View + `viewProperties` |
| view SQL 引用基础表 | `upstreamLineage` + `fineGrainedLineages` |

SQLite 的 view parser 给出一条“无法取得三段式默认 database/schema 名”的 warning，但 view、schema 和 lineage 均成功产生，sink 无 failures。

### 3. 查询日志怎样采集

输入 [`query_history.jsonl`](../demos/route2/datahub/input/query_history.jsonl) 有两条模拟真实 BI 历史 SQL，每条带时间、actor、statement。SQL query source 做了：

```text
Collected 2 queries
num_observed_queries: 2
num_sql_parsed: 2
num_queries_entities_generated: 2
num_query_usage_stats_generated: 2
failures: []
warnings: []
```

生成结果不是一段文本，而是两个 Query 实体以及它们与 `device_orders` 的 subject/usage 关系。后续 `get_dataset_queries` 能按 dataset URN 取回它们。

真实取回的 SQL 包含：

```sql
SELECT product_l1,
       SUM(order_amount) AS device_order_amount
FROM device_orders
WHERE org_code = 'ORG_1001'
  AND year_month BETWEEN 202601 AND 202606
  AND status = 'confirmed'
GROUP BY product_l1
```

这说明查询日志的价值不是“把整段 SQL 丢给大模型”，而是成为有实体关系、可按目标表检索的已用范例。

### 4. SDK 又补了什么

[`enrich.py`](../demos/route2/datahub/enrich.py) 使用真实 DataHub SDK upsert：

- Tag：`CertifiedDeviceMetric` / “已认证设备指标”。
- GlossaryTerm：`device_order_amount` / “设备订货金额”。
- Dataset 中文名和说明。
- Owner：`device_analytics`。
- Custom properties：
  - `required_filter=status=confirmed and explicit org_code`
  - `unit=CNY`
  - `certification=demo_certified`
- PowerBI chart：`device_orders_by_product`。
- PowerBI dashboard：`device_business_h1_2026`。
- dataset 到 BI 对象的输入关系。

最终 URN 记录在 [`sdk_upsert.json`](../demos/route2/datahub/results/sdk_upsert.json)。这里清楚地区分了“数据库连接器观察到的物理事实”和“SDK 写入的业务语义”。

### 5. MCP 暴露哪些工具

启动官方 `mcp-server-datahub`，关闭 mutation/document/user 工具，只保留 6 个只读工具：

```text
search
get_lineage
get_dataset_queries
get_entities
list_schema_fields
get_lineage_paths_between
```

完整原始返回在 [`mcp_calls.json`](../demos/route2/datahub/results/mcp_calls.json)。下面不是示意，而是本机真实调用的压缩版。

#### 调用 1：搜索候选资产

输入：

```json
{
  "query": "/q device+orders",
  "filter": "entity_type = dataset",
  "num_results": 5
}
```

索引稳定后返回 2 个候选：

```json
[
  {"name": "device_orders_by_product", "type": "View"},
  {"name": "设备订货事实表", "urn": "...main.device_orders..."}
]
```

一个重要现象：名称更接近 query 的 view 排在基础表前面。因此 agent 不能把“搜索第一名”当作最终权威表，必须继续检查说明、认证、血缘和历史使用。

#### 调用 2：读取实体业务上下文

输入：

```json
{"urns": "urn:li:dataset:(urn:li:dataPlatform:sqlite,main.device_orders,PROD)"}
```

返回的关键字段：

```json
{
  "name": "设备订货事实表",
  "description": "每行一张设备订货单；取消单不得计入指标。",
  "customProperties": [
    {"key": "required_filter", "value": "status=confirmed and explicit org_code"},
    {"key": "unit", "value": "CNY"},
    {"key": "certification", "value": "demo_certified"}
  ],
  "glossaryTerms": ["设备订货金额"],
  "owner": "device_analytics"
}
```

#### 调用 3：读取字段

```json
{
  "tool": "list_schema_fields",
  "arguments": {"urn": "...main.device_orders...", "limit": 30},
  "returned": 10
}
```

返回字段名、native type、nullable 和 key 状态。对于大表可以用分页/过滤，不需要在第一次搜索里塞入全部字段。

#### 调用 4：读取历史查询

```json
{
  "tool": "get_dataset_queries",
  "arguments": {"urn": "...main.device_orders...", "count": 10},
  "total": 2
}
```

每项带 SQL statement、language、actor、platform 和 subjects。它可以直接作为 Text-to-SQL 的 few-shot 候选，但仍应结合认证、时效和权限筛选。

#### 调用 5：读取下游血缘

```json
{
  "tool": "get_lineage",
  "arguments": {"urn": "...main.device_orders...", "upstream": false, "max_hops": 2},
  "downstreams": [{
    "type": "DASHBOARD",
    "name": "2026 上半年设备经营看板",
    "degree": 1
  }]
}
```

在全新 `v1.5.0.6` 图里，该接口返回 1 个 dashboard 下游；chart 是 dashboard 成员，不额外表现为第二条 dataset lineage。这一行为来自洁净复跑，原先“应该有两个下游”的假设已被修正。

### 6. 写完立刻查询的时序问题

第一次在查询日志写入后立即调用 MCP，`get_dataset_queries.total=0`；等待 OpenSearch 索引刷新后变成 2。这是真实的最终一致性。生产 agent 应：

- 对刚写入的元数据设置短暂重试；
- 不把“暂时没搜到”直接解释为资产不存在；
- 对实体详情与搜索索引结果做区分，强一致的实体 API 和最终一致的搜索不是同一语义。

官方依据：[DataHub](https://docs.datahub.com/)、[官方 MCP server](https://github.com/acryldata/mcp-server-datahub)。官方 MCP README 也给出相同的 agent 流：search → schema → lineage/query examples → query construction。

## 二、OpenMetadata：连接器、Python SDK 和内置 MCP

### 1. 洁净环境

本次使用官方 `1.13.0-release` compose 和 `openmetadata-ingestion==1.13.0.0`。先执行：

```bash
docker compose ... down -v --remove-orphans
```

旧的 bind volume 被精确移动到 ignored runtime 目录，随后从空目录创建：

- MySQL backend/source
- Elasticsearch
- migration job
- OpenMetadata server

服务最终为 `running healthy`。官方 release：[OpenMetadata 1.13.0](https://github.com/open-metadata/OpenMetadata/releases/tag/1.13.0-release)。

### 2. 连接器输入和输出

物理源是真实 MySQL schema `enterprise_demo`，包含：

- `device_orders`：16 行、10 列、主键、非空约束、中文 column comments。
- `device_orders_by_product`：3 行 view。
- `sales_orders`：3 行干扰表。

连接器 recipe 在 [`ingest_mysql_local.yml`](../demos/route2/openmetadata/ingest_mysql_local.yml)。运行官方 Python ingestion CLI，server/client 版本完全匹配：

```text
Server version 1.13.0
Client version 1.13.0.0
CheckAccess: passed
GetSchemas: passed
GetTables: passed
GetViews: passed
Workflow Success: 100%
Errors: 0
```

得到三项表类资产的 FQN：

```text
enterprise_mysql.default.enterprise_demo.device_orders
enterprise_mysql.default.enterprise_demo.device_orders_by_product
enterprise_mysql.default.enterprise_demo.sales_orders
```

为什么 FQN 有四段？OpenMetadata 把 MySQL 表组织为：

```text
DatabaseService → Database(default) → DatabaseSchema(enterprise_demo) → Table
```

### 3. 一个没有隐藏的权限限制

连接器还执行可选 `GetQueries` 检查，但 `demo_reader` 没有读取 `mysql.general_log` 的权限：

```text
SELECT command denied ... for table 'general_log'
mandatory: false
```

因此本次 OpenMetadata 实验成功采集 schema/view，却没有从 MySQL general log 采集查询历史。这不是平台做不到，而是权限输入不满足。它与 DataHub 的 JSONL query-log 成功路径形成了有用对照：

- 想采查询历史，必须事先解决源系统审计日志位置、保留周期、账号授权和脱敏。
- 生产中不应为了“采得更多”直接给 metadata reader 过宽权限；可以使用日志副本或专门审计管道。

### 4. SDK 写入和读回什么

[`enrich_and_read_sdk.py`](../demos/route2/openmetadata/enrich_and_read_sdk.py) 用 exact-version Python SDK 修改表说明，再完整读回实体。真实结果在 [`sdk_context.json`](../demos/route2/openmetadata/results/sdk_context.json)：

```json
{
  "selected_fqn": "enterprise_mysql.default.enterprise_demo.device_orders",
  "description": "设备订货事实表。指标‘设备订货金额’= confirmed 订单的 order_amount 合计；必须显式限定 org_code；单位 CNY；取消单不得计入。",
  "column_count": 10,
  "passed": true
}
```

字段读回示例：

| 字段 | 类型 | 备注 | 约束 |
|---|---|---|---|
| `order_id` | VARCHAR | 设备订货单唯一编号 | PRIMARY_KEY |
| `year_month` | INT | 自然年月，YYYYMM | NOT_NULL |
| `org_code` | VARCHAR | 数据权限组织编码，查询必须显式限定 | NOT_NULL |
| `status` | VARCHAR | confirmed 才计入设备订货指标 | NOT_NULL |
| `order_amount` | DECIMAL | 设备订货金额，CNY | NULL |
| `profit_amount` | DECIMAL | 设备毛利金额，CNY | NULL |

官方建议 SDK 与 server 使用相同版本；SDK 是 `openmetadata-ingestion` 包中的类型安全 API wrapper，实体定义来自 JSON Schema：[Python SDK](https://docs.open-metadata.org/v1.12.x/api-reference/sdk/python)。

### 5. 内置 MCP 返回什么

与 DataHub 的单独 MCP 进程不同，OpenMetadata 1.13.0 直接在运行服务的 `http://localhost:8585/mcp` 暴露 MCP。客户端用本地 JWT 认证，JWT 只保存在 ignored runtime，未打印。

`tools/list` 真实返回 16 个工具：

```text
search_metadata, semantic_search, get_entity_details,
create_glossary_term, create_glossary, patch_entity,
get_entity_lineage, create_lineage,
get_test_definitions, create_test_case, create_metric,
create_classification, create_tag, create_domain,
create_data_product, root_cause_analysis
```

这组工具不仅可读，还包含治理写操作。生产接入必须按用户身份和授权边界配置，不能因为是 MCP 就默认全部放开。

#### 调用 1：search_metadata

输入：

```json
{"query": "device_orders", "entityType": "table", "size": 5}
```

实际返回：

```json
{
  "totalFound": 2,
  "results": [
    {
      "name": "device_orders",
      "entityType": "table",
      "tableType": "Regular",
      "fullyQualifiedName": "enterprise_mysql.default.enterprise_demo.device_orders",
      "columnNames": ["order_id", "order_date", "year_month", "org_code", "product_code", "product_l1", "country", "status", "order_amount", "profit_amount"]
    },
    {
      "name": "device_orders_by_product",
      "tableType": "View",
      "columnNames": ["product_l1", "device_order_amount", "device_profit_amount"]
    }
  ]
}
```

工具说明明确要求下一步直接使用搜索返回的 `entityType` 和 `fullyQualifiedName`，不要让模型自行猜 FQN。

#### 调用 2：get_entity_details

输入：

```json
{
  "entityType": "table",
  "fqn": "enterprise_mysql.default.enterprise_demo.device_orders"
}
```

返回完整表说明、10 个 columns、类型、长度/精度、constraint、字段说明、service/database/schema 引用和变更摘要。`org_code` 的“查询必须显式限定”和表级 `confirmed` 口径都在响应中。

原始 16 工具 schema 和两次调用完整响应在 [`mcp_calls.json`](../demos/route2/openmetadata/results/mcp_calls.json)。官方说明 MCP 直接把统一知识图谱上下文暴露给 ChatGPT、Claude 等客户端：[OpenMetadata MCP](https://docs.open-metadata.org/v1.13.x/how-to-guides/mcp)。

## 三、两套平台怎样被智能体实际使用

### 一个具体而合理的调用序列

假设 agent 收到“设备订货金额”问题，目录层可以这样工作：

1. **窄搜索**：`search("设备订货")` 或 `search_metadata("device_orders")`，得到基础表和视图候选。
2. **读取详情**：不把搜索摘要直接交给 SQL Writer，而是用 URN/FQN 再取 entity details。
3. **读取 schema**：只取候选对象字段，确认 `order_amount`、`profit_amount`、`status`、`org_code`、`year_month`、`product_l1` 都存在。
4. **读取治理信号**：发现基础表已认证、未废弃，且规则要求 `confirmed` 与显式组织。
5. **读取历史用法**：DataHub 返回相同产品分组的历史 SQL，作为高质量 example。
6. **读取血缘**：发现该表供应正式经营看板，权威性进一步上升。
7. **压缩上下文**：只把选中的表、字段、规则、一个或两个示例交给 SQL Writer，避免把整个 catalog 塞入模型。
8. **生成/调用**：优先映射到受治理 metric；没有 metric 时生成 SQL。
9. **校验**：检查表/字段存在、权限过滤存在、SQL 可 EXPLAIN，再执行。

### 两套平台本次可见的差别

| 维度 | DataHub | OpenMetadata |
|---|---|---|
| MCP 形态 | 独立官方 MCP server | 主服务内置 `/mcp` |
| 本次工具数 | 6 个只读工具 | 16 个读写/治理工具 |
| 查询日志 | JSONL source 成功，MCP 返回 2 条 | MySQL general_log 权限不足，本次未采 |
| 业务丰富 | SDK 写 tag、term、owner、custom properties、BI 对象 | SDK patch 表说明，connector 保留中文 column comments |
| 血缘返回 | dataset → dashboard | 本次重点验证搜索/详情，未额外构造 BI 源 |
| 索引一致性 | 实测有短暂 refresh 延迟 | 本次写入后搜索立即成功 |

### 最重要的边界

这些平台返回“结构化上下文”，但不会自动保证：

- 历史 SQL 就是正确 SQL；
- 最热门的表就是权威表；
- 中文注释一定没有过期；
- `org_code` 文档规则已经在查询执行层被强制；
- 用户通过 MCP 看到的所有对象都有实际数据访问权限。

因此目录层要携带来源、时间、认证/废弃和权限信号；执行层仍需路线 1 的强约束或路线 3 的验证器。
