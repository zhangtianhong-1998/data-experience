# 路线 1：MetricFlow、Cube、WrenAI 如何构建，调用时发生什么

## 这条路线解决的不是“找表”，而是“统一计算”

路线 1 的共同模式是：把物理表包装成一个可执行的业务模型，明确指标、维度、关系和口径，再让消费方用结构化请求访问。引擎对请求进行语义解析，生成 SQL，并在数据库上运行。

这类产品不会自动从海量 SQL 中凭空发现全部企业语义。它们的强项是：一旦某条高价值口径经过确认，就能成为可版本化、可验证、可重复执行的合同。

本次三套系统使用相同的 16 行 `device_orders` 数据和相同问题，最终数值全部匹配 golden result。

## 一、MetricFlow

### 1. 输入是什么

MetricFlow 运行在一个真实 dbt 项目里。物理层输入包括：

- dbt seed：16 行订单。
- dbt view：`device_orders`。
- 时间 spine：`all_days`。MetricFlow 的时间范围规划要求存在可用的日粒度时间 spine；第一次没有 `DAY` spine 时校验失败，补齐后通过。

语义输入在 [`device_orders.yml`](../demos/route1/metricflow/device_project/models/device_orders.yml)：

```yaml
semantic_models:
  - name: device_orders
    defaults:
      agg_time_dimension: order_date
    model: ref('device_orders')
    entities:
      - name: device_order
        type: primary
        expr: order_id
    dimensions:
      - name: order_date
        type: time
        type_params: {time_granularity: day}
      - name: org_code
        type: categorical
      - name: product_l1
        type: categorical
    measures:
      - name: confirmed_device_order_amount
        expr: CASE WHEN status = 'confirmed' THEN order_amount ELSE 0 END
        agg: SUM
      - name: confirmed_device_profit_amount
        expr: CASE WHEN status = 'confirmed' THEN profit_amount ELSE 0 END
        agg: SUM
```

然后把 measures 暴露为业务指标：

```yaml
metrics:
  - name: device_order_amount
    label: 设备订货金额
    type: simple
    type_params:
      measure: confirmed_device_order_amount
  - name: device_profit_amount
    label: 设备利润金额
    type: simple
    type_params:
      measure: confirmed_device_profit_amount
  - name: device_profit_margin
    label: 设备利润率
    type: ratio
    type_params:
      numerator: device_profit_amount
      denominator: device_order_amount
```

这里的含义非常具体：取消单在 measure 表达式里被归零，因此任何使用该 metric 的下游调用都会继承同一个口径。

### 2. 构建阶段生成了什么

洁净复跑先执行 `dbt clean`，再执行 `dbt build`。实际输出为：

```text
Found 2 models, 1 seed, 3 metrics, 1 semantic model
device_orders_seed: INSERT 16
PASS=3 WARN=0 ERROR=0
```

dbt/MetricFlow 生成的关键中间产物是：

- `target/manifest.json`：dbt 节点、依赖、列和模型定义。
- `target/semantic_manifest.json`：语义模型、entities、dimensions、measures、metrics。
- `target/graph.gpickle`：MetricFlow 查询规划图。
- `run_results.json`：构建结果。

`mf validate-configs` 的最终结果是 0 errors、0 warnings。

### 3. 调用输入是什么

```bash
mf query \
  --metrics device_order_amount,device_profit_amount \
  --group-by device_order__product_l1 \
  --where "{{ Dimension('device_order__org_code') }} = 'ORG_1001'" \
  --start-time 2026-01-01 \
  --end-time 2026-06-30 \
  --order device_order__product_l1 \
  --explain --show-dataflow-plan
```

这说明智能体或 BI 工具不必自己写聚合 SQL，只要决定：两个指标、一个分组维度、组织过滤和时间范围。

### 4. 中间规划过程是什么

MetricFlow 实际打印的 dataflow 主链是：

```text
ReadSqlSource(device_orders)
  → MetricTimeDimensionTransform(order_date)
  → ConstrainTimeRange(2026-01-01..2026-06-30)
  → Select(metric inputs + product_l1 + org_code)
  → WhereFilter(org_code='ORG_1001')
  → AggregateSimpleMetricInputs
  → ComputeMetrics
  → OrderBy(product_l1)
  → WriteToResultDataTable
```

最终编译 SQL：

```sql
SELECT
  device_order__product_l1,
  SUM(device_order_amount) AS device_order_amount,
  SUM(device_profit_amount) AS device_profit_amount
FROM (
  SELECT
    org_code AS device_order__org_code,
    product_l1 AS device_order__product_l1,
    CASE WHEN status = 'confirmed' THEN order_amount ELSE 0 END
      AS device_order_amount,
    CASE WHEN status = 'confirmed' THEN profit_amount ELSE 0 END
      AS device_profit_amount
  FROM "metricflow-device"."main"."device_orders"
  WHERE DATE_TRUNC('day', order_date)
        BETWEEN '2026-01-01' AND '2026-06-30'
) subq_5
WHERE device_order__org_code = 'ORG_1001'
GROUP BY device_order__product_l1
ORDER BY device_order__product_l1
```

### 5. 输出是什么

[`org1001_h1_by_product.csv`](../demos/route1/metricflow/device_project/results/org1001_h1_by_product.csv) 返回三行；[`verification.json`](../demos/route1/metricflow/device_project/results/verification.json) 的 `match=true`。

### 6. 对企业项目的真实启发

- MetricFlow 明确区分物理 dbt model、entity、dimension、measure 和 metric，适合把“已经确认的核心口径”固化。
- dataflow plan 让“哪个阶段加了时间、组织、聚合”可审计。
- 它不负责从 BI 注释和海量日志中自动发现所有定义；那需要路线 2/3 先产生候选和证据，再进入审定。

官方依据：[MetricFlow GitHub](https://github.com/dbt-labs/metricflow)。官方说明 metric request 会先生成 dataflow query plan，再优化并翻译成特定引擎 SQL。

## 二、Cube

### 1. 输入是什么

Cube 直接连接同一个 DuckDB。语义模型在 [`DeviceOrders.js`](../demos/route1/cube/model/DeviceOrders.js)。核心定义：

```javascript
cube('DeviceOrders', {
  sql: 'SELECT * FROM device_orders',

  measures: {
    deviceOrderAmount: {
      sql: `CASE WHEN ${CUBE}.status = 'confirmed'
            THEN ${CUBE}.order_amount ELSE 0 END`,
      type: 'sum',
      title: '设备订货金额'
    },
    deviceProfitAmount: {
      sql: `CASE WHEN ${CUBE}.status = 'confirmed'
            THEN ${CUBE}.profit_amount ELSE 0 END`,
      type: 'sum'
    }
  },

  dimensions: {
    productL1: {sql: 'product_l1', type: 'string'},
    orgCode: {sql: 'org_code', type: 'string'},
    orderDate: {sql: 'order_date', type: 'time'}
  }
});
```

实际查询输入保存在 [`query.json`](../demos/route1/cube/query.json)。它是 REST API 可接受的结构化对象，而不是 SQL 字符串。

### 2. 调用时中间生成了什么

首先调用 `/cubejs-api/v1/sql`。真实响应保存在 [`sql_response.json`](../demos/route1/cube/results/sql_response.json)，核心内容是：

```json
{
  "sql": [
    "SELECT ... SUM(CASE WHEN status='confirmed' ...) ... WHERE order_date >= ? AND order_date <= ? AND org_code = ? GROUP BY 1 ORDER BY 1",
    ["2026-01-01T00:00:00.000Z", "2026-06-30T23:59:59.999Z", "ORG_1001"]
  ],
  "dataSource": "default",
  "memberNames": [
    "DeviceOrders.deviceOrderAmount",
    "DeviceOrders.deviceProfitAmount",
    "DeviceOrders.productL1",
    "DeviceOrders.orgCode",
    "DeviceOrders.orderDate"
  ]
}
```

可观察的关键点：

- 指标定义中的 `confirmed` 条件进入两个 `SUM(CASE WHEN ...)`。
- 用户/智能体给出的日期和组织进入参数绑定，不是文本拼接。
- `aliasNameToMember` 保留 SQL 别名与语义成员的对应关系。
- 响应还给出 additive、leaf measures、可匹配 pre-aggregation 等规划信息。

### 3. `/load` 返回什么

随后将同一个 query 对象交给 `/load`。真实 [`load_response.json`](../demos/route1/cube/results/load_response.json) 返回：

```json
{
  "data": [
    {
      "DeviceOrders.productL1": "Compute",
      "DeviceOrders.deviceOrderAmount": "7500",
      "DeviceOrders.deviceProfitAmount": "1560"
    },
    {
      "DeviceOrders.productL1": "IoT",
      "DeviceOrders.deviceOrderAmount": "3400",
      "DeviceOrders.deviceProfitAmount": "650"
    },
    {
      "DeviceOrders.productL1": "Network",
      "DeviceOrders.deviceOrderAmount": "3800",
      "DeviceOrders.deviceProfitAmount": "730"
    }
  ],
  "annotation": {
    "measures": {
      "DeviceOrders.deviceOrderAmount": {
        "shortTitle": "设备订货金额",
        "type": "number"
      }
    }
  }
}
```

这里不仅有值，还有供前端/智能体展示的成员注释。

### 4. 实测边界

- Cube 的强项是通过 REST、GraphQL、SQL 等接口提供稳定的消费面。本次真实验证的是 REST `/sql` 与 `/load`。
- 容器第一次接受连接时 API 尚未就绪，原客户端遇到 `RemoteDisconnected`；就绪检测改为容忍暂时断连后通过。这说明生产调用要有 readiness 和重试，不应只以端口已打开为准。
- 模型依然需要被构建或生成；自动挖掘结果要经过治理才能进入该层。

官方依据：[Cube data modeling](https://cube.dev/product/data-modeling)、[Cube getting started](https://docs.cube.dev/docs/data-modeling/overview)、[Measures](https://docs.cube.dev/reference/data-modeling/measures)。Cube 官方明确把 cube/view 作为数据图，把 measure/dimension/access policy 作为统一模型，并通过 API 服务 BI 和 AI agent。

## 三、WrenAI

### 1. Wren 与前两者的不同点

WrenAI 当前开源路线把自己定位为 agent 的 context layer。它不仅有可执行 cube，还把 schema、规则、示例和知识文件通过 MCP 暴露给智能体。因此它处在路线 1 和路线 3 的连接处。

### 2. 输入是什么

模型在 [`models/device_orders/metadata.yml`](../demos/route1/wrenai/device_project/models/device_orders/metadata.yml)：

```yaml
name: device_orders
table_reference:
  catalog: demo
  schema: main
  table: device_orders
columns:
  - name: org_code
    type: VARCHAR
    properties:
      description: "组织编码；分析必须显式限定。"
  - name: product_l1
    type: VARCHAR
    properties:
      description: "产品一级分类。"
properties:
  description: "每行一张订货单，取消单不得计入指标。"
```

可执行 cube 在 [`cubes/device_business/metadata.yml`](../demos/route1/wrenai/device_project/cubes/device_business/metadata.yml)：

```yaml
name: device_business
base_object: device_orders
measures:
  - name: device_order_amount
    expression: SUM(CASE WHEN status = 'confirmed' THEN order_amount ELSE 0 END)
  - name: device_profit_amount
    expression: SUM(CASE WHEN status = 'confirmed' THEN profit_amount ELSE 0 END)
dimensions:
  - name: product_l1
    expression: product_l1
  - name: org_code
    expression: org_code
  - name: year_month
    expression: year_month
```

此外还有自然语言规则 [`device_metrics.md`](../demos/route1/wrenai/device_project/knowledge/rules/device_metrics.md)：

```text
device_order_amount 只合计 status='confirmed' 的 order_amount。
查询必须显式给出 org_code。
“销售金额”属于 sales_orders，不能代替设备订货金额。
```

### 3. 构建阶段生成什么

- `wren context validate --strict` 校验源码。
- `wren context build` 把多个 YAML/知识对象编译为 [`target/mdl.json`](../demos/route1/wrenai/device_project/target/mdl.json)。
- `wren cube query --sql-only` 先生成 modeled SQL。
- 连接 DuckDB 后执行 cube query；`wren dry-plan` 验证物理 SQL 能在目标数据源规划。

第一次连接失败来自 DuckDB 文件路径和 catalog alias 不一致；修正连接 profile 后重建 MDL 即通过。这说明 Wren 的“语义对象名”和“数据连接 catalog/schema”必须一致。

### 4. MCP 怎样使用，返回什么

本次启动了官方 `wren serve mcp`，客户端真实执行 `tools/list`、`get_context` 与 `query_cube`。完整返回在 [`mcp_calls.json`](../demos/route1/wrenai/device_project/results/mcp_calls.json)。

`tools/list` 返回 17 个工具，包括：

```text
run_sql, dry_run, query_cube, dry_plan,
get_mdl, list_models, describe_model, get_data_source,
list_cubes, describe_cube, list_functions,
get_instructions, recall_queries, get_context,
describe_schema, list_stored_queries, list_knowledge
```

给 `get_context` 的输入：

```json
{"question": "ORG_1001 在 2026 上半年按产品一级分类的设备订货金额"}
```

真实返回把上下文压成一段适合模型读取的 schema：

```text
Model: device_orders — 每行一张订货单，取消单不得计入指标
org_code — 组织编码；分析必须显式限定
product_l1 — 产品一级分类

Cube: device_business
Measures:
  device_order_amount = SUM(CASE WHEN status='confirmed' ...)
  device_profit_amount = SUM(CASE WHEN status='confirmed' ...)
Dimensions:
  product_l1, org_code, year_month, status
```

随后调用：

```json
{
  "cube": "device_business",
  "measures": ["device_order_amount", "device_profit_amount"],
  "dimensions": ["product_l1"],
  "filters": [
    "org_code:eq:ORG_1001",
    "year_month:gte:202601",
    "year_month:lte:202606"
  ]
}
```

`query_cube` 直接返回列名、三行结果、`row_count=3`、`truncated=false`。这正是一个 agent 的可用调用面：先拿受治理上下文，再调用 cube，不需要把连接凭证暴露给模型。

### 5. 实测边界

- 官方说明 MCP server 不会在源码改变后自动重建 MDL；必须显式执行 `wren context build`。本次也遵循了这一点。
- 安装 `wrenai[mcp]` 时，最新依赖解析到了不兼容的 MCP 2.0；按当前 Wren 声明约束固定 `mcp>=1.19,<2` 后运行成功。生产环境必须锁版本。
- 本次 `get_context` 因没有安装 memory extra，使用 dependency-free 全量 schema 返回；大规模场景要建立 embedding memory/index，不能把所有 schema 全塞给模型。

官方依据：[WrenAI GitHub](https://github.com/Canner/WrenAI)、[MDL 说明](https://docs.getwren.ai/oss/engine/concept/what_is_mdl)、[MCP 工具与安全说明](https://docs.getwren.ai/oss/guides/mcp)。

## 三者对比：同属路线 1，但接口重心不同

| 观察维度 | MetricFlow | Cube | WrenAI |
|---|---|---|---|
| 核心模型 | dbt semantic model + metric | cube/view + measure/dimension | MDL model/cube + knowledge |
| 中间产物 | semantic manifest + dataflow plan | transformed query + parameterized SQL | compiled `target/mdl.json` |
| 本次调用面 | CLI `mf query` | REST `/sql`、`/load` | CLI + MCP |
| 最强证据 | 可解释查询规划 | API 返回 SQL、bind 与 annotation | agent 可先取 context 再执行 cube |
| 主要局限 | 需 dbt 与显式建模 | 需显式模型与服务部署 | 当前快速演进，需锁版本、主动 build |

如果目的是给 Data Agent 提供稳定计算，三者共同启示是：**让模型选择已命名的 metric/dimension/filter，比让模型每次重新拼聚合 SQL 更可控。**
