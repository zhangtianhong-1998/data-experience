## 三、DbCC 复现：从 58 个字段定义到组件引用

## 3.1 输入是什么

文件：`workspace/dbcc/data/database.json`。

包含：

```text
3 张订单月表
3 张退款月表
1 张区域表
1 张客户表
合计 8 张表、58 个物理列定义
```

专门包含论文描述的三种模式：

1. 每张表重复审计列；
2. 同月份表结构完全相同；
3. 字段说明带重复语义标签。

外部知识文件有五条：净收入、退款状态、区域映射、活跃客户、库存周转。

问题只需要前三条：

> For July 2026, show net revenue by sales region and exclude refunded orders.

## 3.2 第一步：原始表示

输出：`workspace/dbcc/outputs/01_raw_context.txt`。

每张表重复写完整字段、类型、描述和标签。程序计数：

```json
{
  "estimated_units": 58,
  "context_chars": 4875
}
```

这里 `estimated_units` 是论文 gain 公式使用的信息单位数，不是假装精确 token。

## 3.3 第二步：列组因子化

中间文件：

```text
02_factorized_artifacts.json
02_factorized_context.txt
```

程序先建立：

```text
(列名, 类型) → 出现该列的表集合
```

再把拥有同一表集合的列归为候选组件，计算：

```text
gain = support × width - (support + width)
```

最后产生 3 个共享结构组件。

结果：

```text
原始单位：58
因子化单位：39
节省单位：19
减少比例：32.76%
```

## 3.4 第三步：验证是否真的无损

验证器对每张表执行：

```text
残余字段
+ 展开它引用的所有组件
= 恢复字段集合
```

再与原始 `(字段名, 类型)` 集合逐表比较。

结果：

```json
"lossless_schema_recovery": true
```

这能证明本机结构压缩没有丢表和字段；不能证明语义标签一定正确。

## 3.5 第四步：表模板

输出：`03_template_artifacts.json`。

程序将完全同构的月表归入同一模板，并检查较大模板能否以“小父模板 + 少量增量”表达。

本机得到 4 个模板对象。模板不是把物理表合并；每个模板仍保存它覆盖的真实表名。

## 3.6 第五步：共享语义标签

输出：`04_semantic_artifacts.json`。

例如许多字段携带：

```text
audit、datetime、identifier、amount、currency
```

程序按 support 优先选择互不重叠的标签组件，得到 4 个共享组件；每个字段保存组件引用和没有被吸收的残余标签。

这部分是按论文 Algorithm 3 重写的可解释实现。官方代码当前没有以同等完整度交付一套独立 semantic-component strategy。

## 3.7 第六步：问题相关证据

输出：`05_purified_evidence.json`。

五条知识中保留：

```text
metric_definition：净收入公式
value_constraint：退款状态码
concept_to_element：销售区域到表字段的映射
```

删除：

```text
活跃客户定义
库存周转公式
```

本机使用显式 trigger，目的是不需要 API Key 也能稳定演示 typed evidence 的输入输出。论文使用 LLM 做内容抽取，所以本机不能评价其抽取准确率。

## 3.8 第七步：运行作者官方代码

先固定源码：

```bash
./workspace/dbcc/fetch_official_source.sh
```

再运行公开策略类：

```bash
python3 workspace/dbcc/src/run_official_preprocessors.py
```

结果：

| 策略 | 字符数 | 行数 | 相对 raw 字符减少 |
|---|---:|---:|---:|
| raw | 2729 | 74 | - |
| factorization | 1419 | 56 | 48.0% |
| inheritance | 1305 | 37 | 52.2% |

官方输出和自写输出字符数不同，因为 metadata 渲染格式和计数口径不同。两者共同证明的只有：重复 schema 被改写为可展开组件或模板。

## 3.9 DbCC 复现评价

### 已经被证明

- 论文 gain 公式可直接驱动列组选择；
- 重复列组和同构表确实能缩短 schema 表示；
- 压缩结构能展开回全部原字段；
- 官方公开策略在本机同一输入上真实运行；
- 外部知识能够被缩成与问题相关的 typed atoms。

### 没有被证明

- 没有复刻论文的 2.6M → 34.7K token；
- 没有 Spider 2.0-Snow 全量数据库和论文全部配置；
- 没有调用论文所用 DeepSeek-V3.2、GPT-4o、Claude-Opus-4.7 做全量 Schema Linking；
- 没有复算 SRR、NSR、NSP 和端到端 EX；
- 本机 trigger 净化不是论文 LLM 净化精度的替代品。

### 工程判断

DbCC 的结构算子容易落地，也很适合没有行数据的场景。真正难的是：

- 近义字段是否应归一；
- 同名字段是否其实不同义；
- 自动语义标签是否可信；
- 组件版本改变后如何审计。

因此它应当输出候选组件和来源证据，不宜第一次扫描就直接成为全局权威语义。

## 四、CSR-RAG 复现：三路检索的每一个中间对象

## 4.1 为什么是独立实现

截至核验日期，论文、arXiv 页面和检索结果没有给出可验证的官方源码。匿名企业数据也没有公开。

因此本机只能：

- 按论文公式和 Algorithm 1 实现三段数据流；
- 把论文没有公开的选择写明；
- 用公开合成数据验证机制；
- 不声称复现作者私有数字。

## 4.2 输入是什么

`schema.json`：

```text
12 张表
52 个字段
11 条真实外键
```

包括订单、退款、客户、产品、品类、渠道、区域、物流、支付、库存、营销和客服。

`history.json`：8 条：

```text
历史自然语言问题 ↔ 历史 SQL 使用的表
```

`questions.json`：4 个测试问题，每题有 gold tables 和 gold columns。

## 4.3 第一步：建立三个索引

### 历史问题索引

每条文档是：

```text
历史问题 + 已知相关表描述 + 已知字段描述
```

### Schema triplet 索引

每个字段形成：

```text
(field, column_of, table)
```

完整结果保存在 `schema_triplets.json`。

### Relational 字段与超图索引

表为节点，共享列名为超边；真实外键另外保存。结果在 `hypergraph.json`。

## 4.4 第二步：运行 Contextual RAG

对问题 q1：

> For July show net revenue by sales region excluding refunds

取 `k=1`，命中：

```text
h1：monthly gross and net sales by geographic region
相似度：0.542304
表：fact_orders、fact_returns、dim_region
```

这一路干净地给出三张 gold 表。

## 4.5 第三步：运行 Structural RAG

取 `l=10`，前几项：

```text
fact_returns.refund_amount
dim_region.region_name
fact_orders.gross_amount
dim_region.region_id
fact_orders.discount_amount
```

同时出现两个噪声表：

```text
dim_product
marketing_campaign
```

这不是程序 bug，而是向量语义召回的正常表现：成本、预算和收入都与 amount 相关。

## 4.6 第四步：合并候选表

```text
Contextual tables ∪ Structural tables
```

得到五张表。这个阶段倾向 Recall，不会立即删除前两路的候选。

## 4.7 第五步：Relational RAG

本机明确选用：

```text
operator = 表用途 + 字段名 + 字段描述
score = 与问题的 cosine similarity
```

在五张候选表内选前 12 个字段，并添加候选表之间的真实外键端点。

q1 正确添加：

```text
fact_orders.region_id = dim_region.region_id
fact_returns.order_id = fact_orders.order_id
```

也因噪声表添加了一条不需要的 Join：

```text
fact_orders.product_id = dim_product.product_id
```

这是一条重要复现发现：关系阶段可以补全 Join，但如果候选表本身错了，“有效外键”仍可能是与当前问题无关的有效关系。

## 4.8 最终指标

默认配置：

```text
k=1, l=10, h=12
```

| 后端 | 表 P | 表 R | 字段 P | 字段 R | 中位查询检索耗时 |
|---|---:|---:|---:|---:|---:|
| TF-IDF | 52.5% | 91.67% | 38.17% | 80.36% | 约 0.5 ms |
| MiniLM | 77.5% | 100% | 47.61% | 96.88% | 约 36 ms |

MiniLM 索引构建约 0.24 秒；模型初次下载时间不计入查询延迟。

## 4.9 参数扫描发现了什么

| k/l/h | 表 P | 表 R | 字段 P | 字段 R |
|---|---:|---:|---:|---:|
| 1/6/8 | 100% | 100% | 63.33% | 85.57% |
| 1/10/12 | 77.5% | 100% | 47.61% | 96.88% |
| 2/10/12 | 58.75% | 100% | 42.33% | 96.88% |
| 2/18/18 | 37.80% | 100% | 28.07% | 96.88% |

扩大 k/l/h 后：

- 表 Recall 没有继续改善；
- 字段 Recall 从 85.57% 上升到 96.88%；
- Precision 持续下降；
- 再继续扩大时，字段 Recall 也不再提高。

这证明参数必须根据“下游最怕漏字段，还是更怕噪声”选择，不能追求一个脱离任务的最优值。

## 4.10 CSR-RAG 复现评价

### 已经被证明

- 三路检索可以独立实现并串起来；
- Contextual 和 Structural 提供互补候选；
- 普通图能从字段回表；
- 超图/外键关系能补 Join 字段；
- MiniLM 相比 TF-IDF 提升了这个小型数据集的语义召回；
- k/l/h 对 Precision/Recall 有清晰可测的影响；
- 全链路可以在本机几十毫秒级运行。

### 没有被证明

- 没有官方源码一致性；
- 没有匿名企业 benchmark 的 40% Precision/80% Recall 复算；
- 没有作者的具体 embedding checkpoint；
- 没有作者的 operator、metadata 规则和权重；
- 没有下游 SQL 生成与执行准确率；
- 本机约 36 ms 与论文约 30 ms 不可直接比较。

### 工程判断

CSR-RAG 很适合成为你的“候选上下文生成器”，但需要增加四件事：

1. 让历史 SQL 带认证状态、版本和成功率；
2. 图节点不只放表字段，还放指标、术语和 BI 模型；
3. Join 边带来源次数、时间和可信度；
4. 检索后必须做权限、废弃对象和口径冲突过滤。

## 五、两篇论文可以怎样组合

它们解决的不是同一个阶段。

```text
                离线数据库侧
原始海量资产 ──DbCC──> 短小、可逆、结构化的数据库表示
                            ↓
                        建检索索引
                            ↓
                在线问题侧
用户问题 ──CSR-RAG──> 本题相关的表、字段和 Join
                            ↓
                 ContextPacket / Prompt
                            ↓
                 SQL Writer 或 DSL Writer
```

DbCC 回答：

> 全库说明书应该怎样提前整理？

CSR-RAG 回答：

> 当前问题应该从整理后的说明书里取哪些对象？

对你的项目，一个合理的组合是：

1. 从 BI SQL 和模型抽表、字段、Join、表达式；
2. 用 DbCC 思路提取可复用组件、模板和规范语义；
3. 同时建立历史问题索引、语义对象索引和关系图；
4. 提问时用 CSR-RAG 多路召回；
5. 图谱返回少量指标绑定、Join 和过滤，而不是全图；
6. 形成带来源、版本、权限和可信度的 ContextPacket；
7. 让 LLM 生成 DSL，再由语义引擎编译 SQL。

## 六、最终评价

### DbCC 更像“数据资产整理方法”

它对你的知识工程更直接：重复 SQL 表达式、表模板、公共字段、中文别名和业务文档都可以在离线阶段变成可复用对象。

但不要把自动组件立即升级成权威知识。组件必须可追溯、可展开、可版本化。

### CSR-RAG 更像“Agent 上下文选择方法”

它告诉你建完知识后怎样用：

- 历史问题召回真实经验；
- 结构图召回新对象；
- 关系图补 Join；
- 最后只交付局部上下文。

但论文没有解决口径冲突、权限、过期知识和最终 SQL 正确性。

### 我建议下一步怎样验证

不要继续扩大合成表规模，而应从你的真实资产抽一个可匿名的业务域：

```text
50-200 张表
200-500 条 BI SQL
50 个真实问题
人工标注正确指标、表、字段、Join 和过滤
```

做四组对照：

1. 只用原始 schema；
2. schema + 单路向量检索；
3. DbCC 表示 + 单路检索；
4. DbCC 表示 + CSR 多路检索 + 图关系。

分别测：

- 正确指标 Top-k Recall；
- 正确表和字段 Recall；
- 唯一正确 Join 路径命中率；
- Context token；
- SQL 执行准确率；
- 每个问题耗时；
- 错误来自检索、口径、Join 还是 SQL 生成。

只有第四组在真实问题上稳定优于第二组，才证明知识图谱和压缩层为你的 Data Agent 带来了额外价值。
