# 先读这份：三条路线到底怎样把一个业务问题变成答案

## 结论先说

三条路线不是三选一，它们处在不同层：

1. **路线 1 是“可执行的指标合同”**。人先定义哪些字段是维度、哪些表达式是指标、哪些过滤条件属于口径；引擎接到结构化查询后，编译 SQL 并执行。
2. **路线 2 是“企业资产与上下文目录”**。连接器把数据库、视图、BI、查询日志等资产采进来，SDK 或治理流程补上中文定义、负责人、标签、血缘；MCP 再把这些信息按需交给智能体。它通常不直接替智能体完成业务计算。
3. **路线 3 是“从自然语言到 SQL 的决策和纠错过程”**。它利用路线 2 一类的上下文，也可以把路线 1 的受治理指标当作执行接口，然后完成候选召回、重排、字段选择、SQL 编写、验证和修复。

最关键的认识是：**“语义数据”不是一张万能知识图谱。** 它至少包含两种不同性质的东西：

- 可被引擎强制执行的语义：指标表达式、维度、关系、默认时间字段、访问规则。
- 帮助智能体做选择的语义：表/字段说明、业务术语、认证与废弃状态、历史查询、常见过滤、BI 血缘、负责人、产品域。

前者让同一个请求算出同一个数，后者让智能体知道该请求应该落到哪个对象、为什么。

## 我用一个什么问题贯穿全部实验

用户问题：

> 请统计 ORG_1001 在 2026 年上半年按产品一级分类的设备订货金额和设备利润，只统计已确认订单。

这个问题故意包含五种企业语义：

| 用户说法 | 系统最终需要的语义 |
|---|---|
| 设备订货 | 应选 `device_orders`，不能选名称相近的 `sales_orders` |
| 设备订货金额 | `SUM(order_amount)` |
| 设备利润 | `SUM(profit_amount)`，与订货金额使用同一批订单 |
| 已确认 | `status = 'confirmed'`，取消单不能计入 |
| ORG_1001 | 必须显式下推 `org_code = 'ORG_1001'`，既是过滤也是权限边界 |
| 2026 上半年 | `year_month BETWEEN 202601 AND 202606` 或等价日期范围 |
| 按产品一级分类 | `GROUP BY product_l1` |

物理库还放入了三个干扰：`sales_orders`、已废弃的 `deprecated_device_orders` 描述，以及一条 `cancelled` 设备订单。这样可以观察系统是在“理解并执行口径”，还是碰巧把金额列求和。

## 路线 1 实际发生了什么

以 Cube 为例，输入不是一句自然语言，而是如下结构化语义请求：

```json
{
  "measures": [
    "DeviceOrders.deviceOrderAmount",
    "DeviceOrders.deviceProfitAmount"
  ],
  "dimensions": ["DeviceOrders.productL1"],
  "timeDimensions": [{
    "dimension": "DeviceOrders.orderDate",
    "dateRange": ["2026-01-01", "2026-06-30"]
  }],
  "filters": [{
    "member": "DeviceOrders.orgCode",
    "operator": "equals",
    "values": ["ORG_1001"]
  }]
}
```

Cube 读取事先声明的指标：

```javascript
sql: `CASE WHEN ${CUBE}.status = 'confirmed'
      THEN ${CUBE}.order_amount ELSE 0 END`,
type: 'sum'
```

中间生成的不是摘要文字，而是一条带参数的 SQL：

```sql
SELECT product_l1,
       SUM(CASE WHEN status = 'confirmed' THEN order_amount ELSE 0 END),
       SUM(CASE WHEN status = 'confirmed' THEN profit_amount ELSE 0 END)
FROM device_orders
WHERE order_date >= ? AND order_date <= ? AND org_code = ?
GROUP BY 1
ORDER BY 1
```

绑定值为 `2026-01-01`、`2026-06-30`、`ORG_1001`。然后 `/load` 执行 SQL，返回三行数值。MetricFlow 做的是同一类工作，但中间还展示 dataflow plan；WrenAI 则把 MDL、业务规则文件和查询能力一起通过 MCP 暴露。

所以路线 1 的回答是：**指标层怎样使用？智能体先把自然语言转换成指标、维度、时间范围和过滤器，指标引擎再负责生成受治理 SQL。** 智能体不应重新发明 `confirmed` 口径。

## 路线 2 实际发生了什么

以 DataHub 为例，资产不是人工逐张录入的。本次真实运行按下面的顺序发生：

```text
SQLite 连接器
  ├─ 扫描数据库与 schema
  ├─ 扫描 3 张表和 1 个视图
  ├─ 读取 10 个字段、类型、主键、空值约束
  └─ 解析视图 SQL，产生表级/字段级血缘

SQL query-log 连接器
  └─ 读取 2 条历史 SQL，解析涉及表、字段、过滤和聚合

DataHub SDK
  ├─ 写入中文说明
  ├─ 写入 glossary term“设备订货金额”
  ├─ 写入 required_filter、单位、认证状态、owner、tag
  └─ 建立 dataset → PowerBI dashboard 的关系
```

智能体随后调用真实 DataHub MCP：

1. `search` 返回候选 `device_orders_by_product` 和“设备订货事实表”。
2. `get_entities` 返回中文说明、`required_filter=status=confirmed and explicit org_code`、单位、认证、负责人和 glossary term。
3. `list_schema_fields` 返回 10 个字段。
4. `get_dataset_queries` 返回两条实际历史 SQL，其中一条已经包含 H1、ORG_1001、confirmed 和按产品分组的使用模式。
5. `get_lineage` 返回下游 PowerBI 看板“2026 上半年设备经营看板”。

注意：MCP 到这里返回的是**上下文**，不是最终业务答案。下一步通常由智能体把这些内容压缩成 prompt/context，选择表和字段，再生成 SQL；或者将问题映射成路线 1 的结构化指标请求。

OpenMetadata 的实验也走完了同样的采集—丰富—读取链。它的内置 `/mcp` 返回了 16 个工具；`search_metadata` 返回 2 个相关对象，`get_entity_details` 返回表说明、10 个字段、主键/非空约束与中文字段备注。

## 路线 3 实际发生了什么

LinkedIn 公开的是论文与工程文章，不是完整生产源码。因此这里做的是“按公开架构可核验地重建”，边界在结果中明确标注。

一次请求的完整轨迹是：

```text
用户 + 产品域
  ↓ 根据用户—表访问矩阵做 FastICA 软聚类
4 张候选表
  ↓ 表索引 + 示例 SQL 索引 + 域知识 + 行业黑话
多路召回
  ↓ 第 1 次 LLM：表重排
device_orders 11.48 分；废弃表 -98.88 分
  ↓ 只对排在前面的表取完整 schema
第 2 次 LLM：字段两级筛选
  ↓ 拼装问题、schema、历史 SQL、术语、口径和规则
第 3 次 LLM：SQL Writer
  ↓ sqlglot 标识符/只读检查 + 业务规则检查 + DuckDB EXPLAIN
SQL 首次通过
  ↓ 执行并与 golden result 比较
三行正确结果
```

为了证明纠错链不是纸面设计，又注入了不存在的 `device_order_fact`：

- 验证器报出未知表、越界表以及 6 个未知字段。
- 第 4 次 LLM（Researcher）从表索引中找到认证且未废弃的 `device_orders`。
- 第 5 次 LLM（Fixer）只替换错误表，保留 `org_code`、上半年、`confirmed` 三个过滤。
- 修复 SQL 再次通过。

最终记录为 5 次真实模型调用、5 次成功、0 次 fallback；API key 和 base URL 没有进入结果或日志。

## 三条路线连起来时，一个智能体会怎样工作

下面是由本次实测能力推导出的具体调用方式，不是要求现在就照搬的自研方案：

```text
“ORG_1001 上半年设备订货和利润，按一级产品”
  │
  ├─ 路线2/MCP：搜索“设备订货”
  │    返回权威表、废弃信号、字段、术语、历史 SQL、BI 血缘
  │
  ├─ 路线3/Agent：检索与重排
  │    选择 device_orders，识别 required_filter 与时间表达
  │
  ├─ 优先路线1：调用受治理指标
  │    measures=[device_order_amount, device_profit_amount]
  │    dimension=product_l1
  │    filters=[org_code, H1]
  │
  ├─ 若没有成熟指标：路线3 生成 SQL 并校验
  │
  └─ 执行 → 三行结果 → 连同口径、来源和校验状态返回
```

这也解释了为什么只做一个知识图谱不够：目录能告诉智能体“哪里有什么”，但只有可执行指标或严格 SQL 校验能约束“怎么算”；只有自然语言编排层才能处理模糊问题、候选冲突和失败恢复。
