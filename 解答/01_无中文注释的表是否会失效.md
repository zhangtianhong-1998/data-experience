# 没有中文注释、开发人员也不知道含义的表，会不会失效？

## 先给结论

不会立刻“完全失效”，但不能直接把它当成可信语义层交给智能体。

它会发生的是**能力降级**：

- 数据库仍然可以按技术字段名查询。
- Cube、MetricFlow、WrenAI 仍然可以生成或承载一个只有表名、字段名、类型的模型骨架。
- 但自然语言到字段、指标和统计口径的映射会明显失准。
- 如果系统没有任何额外证据，就不能知道 `amt` 是含税金额、未税金额、订货金额还是回款金额，也不能知道 `st='C'` 代表 confirmed 还是 cancelled。
- 这类对象应进入“未知语义区”，而不是让大模型根据字段名自行猜测。

真正合理的做法不是把整张表删除，也不是强行生成中文释义，而是让表沿着“未知 → 候选 → 已治理”的状态逐步升级。

![无语义注释表的分级处理流程](./assets/无语义表处理流程.svg)

这张图最重要的信息是：没有解释的表不会被删除，而是先留在 `Unknown` 区域；只有找到足够的外围证据，经过冲突检查和验证后，才逐步进入正式语义层。图的可编辑源码在 [`无语义表处理流程.mmd`](./assets/无语义表处理流程.mmd)。

## 一、为什么表头本身不等于语义

假设数据库里只有：

```text
t_ord_dtl
  id
  amt
  st
  org_cd
  dt
```

从结构上可以确定：

- 有一张表。
- 表里有五个字段。
- 可以读取字段类型、是否为空、是否为主键。
- 如果数据库声明了外键，还可以得到部分表关系。

但仅凭这些信息不能确定：

- 一行代表订单、订单明细、发货记录还是每日快照。
- `amt` 的币种、单位和统计口径。
- `st` 每个编码的业务含义。
- `dt` 是创建时间、确认时间还是记账时间。
- 多张表中哪一张是当前有效的权威数据源。
- 哪些记录应该排除。
- 哪些用户可以查看哪些组织的数据。

这不是 Cube、WrenAI 或大模型的某个功能没有做好，而是**信息在输入资产中根本不存在**。不存在的业务事实无法通过算法可靠恢复。

## 二、在你的数据条件下，仍然可以从哪里恢复含义

你的项目并不是只有裸表头。你还有 BI 看板 SQL、BI 引擎中间组件、查询日志、物理元数据和部分中文注释。这些资产能够提供“使用行为证据”。

| 证据 | 可以提取什么 | 例子 |
|---|---|---|
| SELECT 表达式 | 候选指标公式、别名 | `SUM(CASE WHEN st='C' THEN amt ELSE 0 END) AS 设备订货金额` |
| GROUP BY | 常用分析维度和粒度 | `GROUP BY product_l1, org_cd` |
| WHERE | 默认过滤、状态口径、权限痕迹 | `st='C' AND org_cd=?` |
| JOIN | 表关系和连接键 | `a.product_id=b.product_id` |
| 看板标题和控件 | 中文术语、同义词、时间语义 | “设备订货趋势”“组织”“产品一级分类” |
| 重复查询模式 | 口径稳定性和使用热度 | 多个看板重复使用同一段计算表达式 |
| ETL/dbt/血缘 | 上下游来源、权威表候选 | 明细表 → 汇总表 → 认证看板 |
| 用户与权限日志 | 领域归属和可见范围 | 某部门只查询自己的 `org_cd` |

例如，多个独立看板都反复出现：

```sql
SUM(CASE WHEN st = 'C' THEN amt ELSE 0 END)
```

其中一个看板把它显示为“设备订货金额”。系统可以提出如下候选：

```yaml
candidate_metric:
  name: device_order_amount
  source_expression: SUM(CASE WHEN st = 'C' THEN amt ELSE 0 END)
  possible_label: 设备订货金额
  evidence:
    - BI 看板标题和字段别名
    - 多个 SQL 中重复出现的表达式
    - st='C' 与 amt 同时出现
  status: candidate
```

注意它仍然只是候选。系统不能因为某一次 SQL 使用了这个表达式，就断言全公司“设备订货金额”都必须这样算。

## 三、这类表在三个阶段分别能做什么

| 状态 | 系统知道什么 | 能否交给自然语言智能体 | 推荐行为 |
|---|---|---|---|
| Unknown | 表名、字段名、类型 | 不应直接开放 | 保存元数据；检索外围证据；必要时询问用户 |
| Candidate | 有推测语义和证据链，但未确认 | 可以辅助检索，不能冒充权威口径 | 返回候选、置信原因和冲突；执行时明确标记 |
| Governed | 口径、粒度、关系、权限已验证 | 可以 | 编译为 Cube/MDL/MetricFlow 并用于正式查询 |

因此，所谓“失效”不是一个二元开关。

- 对数据库技术人员的精确 SQL 查询，它没有失效。
- 对自然语言字段匹配，它可能严重退化。
- 对企业可信指标，它在被确认之前应视为不可用。
- 对知识挖掘系统，它仍是一个等待补充证据的资产。

## 四、提问时应该怎样处理未知表

用户问：

> 看一下今年上半年各产品的订货金额。

如果系统只有 `amt`、`st`、`dt`，不应该直接生成：

```sql
SELECT product, SUM(amt) ...
```

因为这偷偷假设了：

- `amt` 就是订货金额。
- 所有状态都应该统计。
- `dt` 就是订货日期。
- `product` 的统计粒度正确。

合理的响应路径是：

1. 检索已治理指标中是否有“订货金额”。
2. 如果没有，检索 BI SQL、看板标题、历史查询和血缘中的候选表达式。
3. 如果找到唯一且证据充分的候选，展示采用的口径和证据，再执行或请求确认。
4. 如果存在多个候选，询问用户选择“设备订货金额”“销售订单金额”还是“含税订货金额”。
5. 如果没有任何证据，明确说无法仅凭 `amt` 判断含义，并请求表 Owner 或业务用户补充。

这比“无论如何都返回一条 SQL”更符合企业级智能体的要求。

## 五、没有数据本身会带来的额外边界

你的数据源没有真实业务数据，因此系统无法依赖值分布来判断：

- `st` 中究竟有哪些值。
- `amt` 是元、万元还是美元。
- `org_cd` 是否真的是组织编码。
- 某列是否包含个人信息。
- 主外键是否在真实数据上满足唯一性。
- 某个 Join 是否会产生一对多放大。

这些问题可以通过 SQL 结构和日志提出候选，但不能完成数据级验证。生产系统需要把“结构证据”和“数据验证结果”分开保存，避免把推断伪装成事实。

如果未来允许在数据源侧执行受控探测，但仍不把明细数据带出来，可以只返回：

- distinct 数量和空值率。
- 枚举值及脱敏后的频次。
- 最小值、最大值、数据类型一致性。
- 主键唯一性和 Join 基数。
- 预定义指标的聚合校验结果。

这样能补充验证证据，又不需要复制业务明细数据。

## 六、适合你项目的落地规则

建议每个字段、指标、关系都保存以下状态：

```json
{
  "semantic_status": "unknown | candidate | governed | rejected",
  "proposed_meaning": "候选业务含义",
  "evidence": [
    "来自哪些 SQL、看板、注释或血缘"
  ],
  "conflicts": [
    "存在哪些互相矛盾的解释"
  ],
  "owner": "谁有资格确认",
  "last_verified_at": "最后确认时间",
  "allowed_for_agent": false
}
```

其中最重要的规则是：

> 大模型可以生成候选和解释证据，但不能仅凭猜测把 Candidate 自动升级为 Governed。

## 最终判断

如果一张表同时满足以下条件：

- 没有中文注释。
- 字段名没有可解释性。
- 没有 SQL 或看板使用记录。
- 没有血缘。
- 没有样例值或受控统计。
- 找不到业务 Owner。

那么它的业务语义在原则上就是不可识别的。任何系统给出的中文解释都只能是猜测。

但你的场景中还有大量 BI SQL 和中间组件数据，所以更现实的结论是：**一部分语义可以从使用行为中自动提出候选，另一部分必须通过冲突检测、执行验证和少量定向确认逐步补齐。**这正是知识挖掘系统应该解决的问题，而不是要求所有表先由人工完整注释。
