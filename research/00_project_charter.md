# 企业 BI 资产语义挖掘与 Data Agent 增强：项目章程

更新时间：2026-08-03

## 1. 项目的真实目标

本项目的目标不是“从 SQL 中抽取若干指标、维度并画成知识图谱”，也不是把知识图谱降格为历史 SQL 的检索索引。

项目要从集团已经存在的 BI 报表、组件、数据集、中间模型、SQL、字段血缘、物理表元数据、字段注释和查询历史中，持续挖掘业务语言、分析意图、指标口径、数据实现和使用关系，形成一套可追溯、可增量演化、能被机器消费的企业语义体系。

它最终要连接四个原本分离的世界：

```text
集团业务语言
    ↕
业务概念与统计口径
    ↕
数据资产与计算实现
    ↕
用户问数行为与 Data Agent 执行过程
```

这套体系应成为 Data Agent 的语义控制平面：帮助智能体理解问题、发现数据、消除歧义、规划分析、生成或改写 SQL、校验结果、解释答案，并支持企业语义治理。

## 2. 两个必须同时解决的问题

### 2.1 如何构建高质量语义

从没有行级数据、主要依赖元数据和历史 SQL 的海量资产中，构建下列知识：

- 业务实体、事件、属性、维度、度量和指标；
- 指标定义、计算表达式、聚合方式、过滤条件、时间范围、单位、粒度和适用组织；
- 术语、别名、近义词、上下位词、同名异义和口径变体；
- 报表、组件、数据集、查询、表、字段和概念之间的实现与证据关系；
- 查询规范、历史使用、权限约束、质量状态、版本和影响关系；
- 局部概念、报表概念与集团标准概念之间可撤销的映射。

### 2.2 如何让语义真正服务 Data Agent

知识只有进入问数链路并产生可测量收益才有价值。目标使用能力包括：

- 用户术语识别、别名扩展和上下文消歧；
- 业务概念到报表、组件、数据集、表、字段和 SQL 实现的检索；
- Schema Linking 候选压缩和排序；
- 指标口径、时间粒度、过滤条件、Join 路径和计算表达式的选择；
- 历史 SQL 的结构复用、参数适配、权限检查和执行前验证；
- 查询计划生成、结果口径解释和证据引用；
- 数据或口径变化后的影响分析；
- 对不确定、冲突和越权请求发起有针对性的澄清。

## 3. 不可回避的现实约束

1. 规模可能达到百万级报表组件，不能做全量两两匹配。
2. 不具备大规模众包或专家精标资源，人工只能处理高价值或高风险例外。
3. LLM 成本敏感，不能为每条资产固定执行多轮抽取和复核。
4. 不同用户构建的报表和物理表高度异构，不能假设存在统一模板。
5. 当前没有行级数据，无法依赖真实值分布完成所有语义判断。
6. 错误合并会污染所有下游关系，因此全局融合应偏向高精度、保守合并。
7. 所有自动知识必须能追溯、重算、撤销和版本化。
8. 权限必须继承底层数据资产约束，语义检索不能绕过授权边界。

## 4. 目标知识体系不是单层图谱

建议将目标模型理解为六个互相关联但职责不同的层。领域不是当前必选层级；
部门是第一轮可验证、可管理的小集合边界：

```text
L0 源资产与版本事实层
   Report / Component / Dataset / Query / SQL AST / Table / Field / Lineage / Permission

L1 证据与声明层
   Evidence / ExtractionRun / ConceptMention / Claim / QualityIssue

L2 报表局部语义层
   ComponentConcept / ReportConcept / ObservedLabel / LocalMetricDefinition

L3 部门语义层
   DepartmentConcept / DepartmentMetric / LocalAlias / LocalVariant / LocalConflict

L4 集团标准语义层
   CanonicalConcept / MetricDefinition / BusinessEntity / Event / Rule / Variant

L5 Agent 服务与反馈层
   UserQuestion / RetrievalCandidate / QueryPlan / GeneratedSQL / ExecutionOutcome / Feedback
```

其中：

- L0 和 L1 应尽量由确定性程序、SQL AST、元数据规则和可验证引用构建；
- L2 允许保留报表内部表达和不确定声明；
- L3 只在同一部门的小集合内做跨报表候选发现和保守对齐；
- L4 从多个已经验证的部门语义中逐步形成集团标准，不覆盖局部事实；
- L5 既消费语义，也为语义质量提供实际反馈信号。

部门是组织责任边界，不等同于业务领域。如果未来发现跨部门领域确有稳定价值，
可以把 `domain` 作为正交分类或检索维度增加，而不改变上述主链路。

## 5. 构建策略的核心原则

### 5.1 先声明，后融合

LLM 输出首先是“基于某一版本证据生成的一条知识声明”，不是企业唯一真值。局部概念可以长期共存，再通过 `maps_to`、`alias_of`、`variant_of`、`broader_than`、`related_to` 或 `conflict_with` 等关系逐步对齐。

### 5.2 局部优先，全局按需扩展

先利用一个报表内多组件的共同上下文形成局部语义，再在同一部门内通过候选召回进行跨报表对齐。共享物理表只能作为候选信号之一，公共维表、权限表、技术表和临时表需要过滤或降权。部门外的候选默认不进入第一轮实验。

### 5.3 确定性事实优先于生成式推断

SQL 结构、表字段引用、聚合、过滤、分组、Join、血缘、身份和版本应尽可能用解析器或规则提取。LLM 主要处理命名、语义归纳、歧义识别、候选判断和缺失信息说明。

### 5.4 多步算子按风险路由，而非固定多轮

抽取、校验、对齐、冲突审计是可独立调度的算子。默认一次抽取；只有程序校验失败、候选模糊、簇内冲突或高风险变更时才升级到额外模型判断或人工审核。

### 5.5 指纹服务于追溯与复用，不替代语义

至少需要区分资产版本指纹、查询实例指纹、参数化查询模板指纹、证据包指纹、抽取运行指纹和模型/提示词版本。指纹用于变化检测、缓存复用、来源追踪和重算，不应把不同过滤值、单位或口径误合并。

### 5.6 错误知识的成本必须进入系统设计

不能只追求召回率。系统要显式测量错误合并、错误映射和错误口径对 Data Agent 的负面影响，并支持隔离、降级、回滚和拒答。

## 6. 本项目明确不追求的目标

- 不追求第一轮就得到完整、唯一且精细的集团本体；
- 不进行全量概念笛卡尔积或无界的共享表大包分析；
- 不依赖固定四轮 LLM 调用换取表面上的完整度；
- 不把名称相似直接等同于同一概念；
- 不把局部概念强行覆盖为集团标准概念；
- 不把历史 SQL 原样检索后直接执行；
- 不以图中节点和边的数量作为主要成功指标；
- 不把某一种图数据库、向量数据库或语义层产品预设为最终答案。

## 7. “有用”的验收标准

### 7.1 构建质量

- Provenance Coverage：语义声明具备可解析证据引用的比例；
- Extraction Validity：结构、引用、类型和约束校验通过率；
- Incremental Reuse：输入未变化时无需重新调用模型的比例；
- Conflict Isolation：冲突知识未被错误自动合并的比例；
- Cost per Asset：每个报表、组件或变更的模型和计算成本；
- Freshness：源资产变化到语义更新可用的延迟。

### 7.2 检索与 Schema Linking

- Component / Dataset / Table / Field / SQL Recall@K；
- MRR、nDCG 和候选压缩率；
- 权限过滤后的有效召回率；
- 同义表达、命名漂移和口径变体下的鲁棒性；
- 错误知识注入后的性能下降幅度。

### 7.3 Data Agent 端到端收益

- 表、字段、Join、过滤、聚合和指标口径选择正确率；
- SQL 执行正确率与结果语义正确率；
- 首次回答成功率和澄清次数；
- Prompt Token、端到端延迟和单位问题成本；
- 可解释答案的证据覆盖率；
- 语义层导致的错误放大率或回归率。

评估必须至少比较：

```text
基线 Agent
vs Agent + 元数据/向量检索
vs Agent + 局部语义与证据图
vs Agent + 局部语义、历史 SQL 与集团概念层
```

## 8. 对当前本机原型的校准

当前版本已经具备以下可保留基础：

- 以 Report → Component → Dataset → SQL → PhysicalTable 组织事实；
- 处理路径噪声、重复 SQL、多表查询和部分异常；
- 为证据生成 `evidence_id`；
- 让 LLM 只输出候选 annotation / relation；
- 校验 `target_id`、`evidence_id` 和关系引用；
- 保存运行清单、事实、证据包、模型结果和验证报告。

因此，共享对话中“完全没有证据引用”的批评已被当前版本部分解决。

当前仍缺少的关键闭环包括：

- 生产级 SQL AST 与方言支持；
- BI 平台原生稳定 ID 和完整限定物理对象 ID；
- 查询实例、查询模板、参数和源版本的分离；
- ComponentConcept / ReportConcept / CanonicalConcept 的明确分层；
- 百万级跨报表候选召回、保守融合与簇一致性机制；
- 权限、质量、时效性和变更影响的统一建模；
- 面向 Data Agent 的检索 API、规划接口和运行时策略；
- 基于历史组件与 SQL 的离线回放评测；
- 端到端 Data Agent 消融实验。

## 9. 对后续公开研究和开源方案探索的要求

每个候选项目或研究不能只记录“支持知识图谱/语义层”。至少要回答：

1. 它解决 L0-L4 中的哪一层？
2. 输入是否适配无行级数据、以 SQL 和元数据为主的场景？
3. 是否支持证据、版本、血缘、增量和撤销？
4. 百万级资产的候选生成、索引和成本模型是什么？
5. 如何处理同义、变体、冲突和局部概念共存？
6. 如何执行权限过滤和治理？
7. Data Agent 在运行时如何消费它？
8. 是否有可复现评测，指标是否对应实际问数收益？
9. 哪些部分可以直接复用，哪些只能借鉴思想？
10. 在本机最小实验中能否被当前原型的数据结构验证？

## 10. 一句话项目定义

> 从集团既有 BI 和数据资产中持续挖掘可追溯的业务语义、统计口径与数据实现，构建局部优先、保守融合、可增量演化的企业语义控制平面，并用 Data Agent 在问题理解、数据发现、Schema Linking、分析规划、SQL 生成、权限校验、结果解释和语义治理上的可测量收益验证其价值。
